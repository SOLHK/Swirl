# Swirl 工程复杂度与 CI 成本控制规范

生效范围：Swirl 的所有开发人员、AI 编码代理（包括 Gemini/Codex）、PR 与 CI 维护。与 `AGENTS.md` 及发布安全规则共同执行；冲突时不降低安全、数据保护、源码身份及正式发布门槛。

## 1. 先解决真实问题，拒绝无目的堆叠

- 每项改动先写清：用户问题、可重现证据、根因、受影响模块、明确的非目标、最小验收条件。
- 优先修改现有的权威实现；禁止复制第二套运行时、控制器、状态源、缓存、代理核心或故障恢复流程。
- 禁止为假想的极端场景无端增加通用封装、回退、重试、日志、诊断脚本、抽象层、测试矩阵或新依赖。涉及安全、数据完整性、网络/TUN、异步竞态等风险时，必要的防护必须保留。
- 只删除经引用搜索、运行路径与测试证明确实无用的代码；不得因为“精简”破坏用户数据、配置迁移、功能兼容、许可证义务或已有安全边界。
- 同一个缺陷的修复不要扩展成多个无关模块的大规模重构；确认属于同一根因时可完整修复跨层调用链。

## 2. 变更规模与代码所有权

- 一个 PR 以一个独立目标为主；默认争取不超过 **20 个生产源文件、1000 行人工编写代码变更**（新增+删除；不计文档、生成文件、依赖锁文件及独立测试数据）。这是**审查与拆分触发线，不是鼓励压缩代码或删测试的硬上限**。
- 超过时先按功能/层次拆成多个可独立验证的 PR；确需跨层原子改动，应在 PR 中列出涉及模块、不可拆原因、测试范围及维护者批准。不得为规避阈值而拆碎一个必须原子修复的问题。
- Qt/QML/C++ 负责 UI 与协调，`core/` Rust 是唯一代理网络运行时。保持源所有权与接口边界，禁止重新引入外部代理核心。
- 无论代码量多少，严禁同一事实的多处可写状态来源、重复回退路径和无所有权的常驻任务。

## 3. 测试分层：高信号、不过度验证

1. **开发内循环**：仅执行与当前改动相关的格式/静态检查、增量构建、明确复现该缺陷的定向测试。不得为了微小修复先运行整套慢速矩阵。
2. **PR 集成**：保留改动影响到的接口、Qt/QML/Windows/Rust、网络及安全测试。路径分类不确定、跨层触及关键接口时，保守升级测试范围。
3. **`test` 候选与正式发布**：保留所有现有必需的最终源码身份、Qt/MSVC/Rust 配对、TLS/证书、TUN 权限与恢复、DNS/代理、安装升级卸载、真实 UI/动画等验收；`main` 继续严格执行既有发布授权机制。

- 新增测试必须明确对应：复现的失败、用户可见行为变更、真实的兼容性边界或重要安全不变量。优先扩充现有测试而不是复制脚本/新增整套 CI。
- 新增 CI 作业、重复证据集或额外负向控制，需说明原有验证缺口、为何现有流程不能覆盖、可量化成本，以及替代或合并对象；不得无理由无限追加。
- 能通过确定性复现、有效缓存、共享构建产物、正确路径分流、分组和并行执行减少时间；测试仍需使用**与该提交匹配的真实构建产物**，不能拿旧提交的绿色结果冒充通过。
- 不得为图 CI 通过而静默丢弃警告、弱化断言/阈值/超时要求、禁止关键检查、伪造证据、吞掉异常、修改需求或跳过受影响的安全测试。
- 如果优化涉及移除或改变**当前必需的安全/正式交付门槛**，必须先有等价可验证覆盖并得到仓库所有者明确批准；未经批准保持现状。
- 文档与 AI 指令不等于实际 GitHub 分支保护规则；不能声称“写了规定”就已经由 GitHub 自动强制执行。

## 4. CI 失败处理

- 先核对**最新 HEAD** 的 CI；记录失败 run/job/step、日志、产物及首次失败断言。不要凭先前 PR 描述或历史结论推断当前状态。
- 把问题归类为产品缺陷、测试用例缺陷、环境/依赖缺陷或未确定，分别记录事实和假设。
- 先调查同一个失败的证据与最小复现，再修根因；不要无假设地反复重跑完整 CI，更不要一失败就新增专项守卫。
- 修改 UI/Qt 或动画时不允许掩盖真实 QML/VME 警告；运行时补丁须保留来源、ABI 和配套部署身份验证。
- 一个测试已由另一个适用测试等效覆盖时，应提供明确覆盖映射、旧/新成本与验证依据，评估合并，而不是简单删除。

## 5. 每个 PR 必须交付的审计信息

- 变更动机、目标/非目标、根因证据、受影响模块、生产代码文件数/改动行数；
- 新增模块、回退、防御、测试、诊断或 CI 作业的**必要性说明**；无新增则注明无；
- 运行过的定向检查、CI run URL、与当前 HEAD 的对应关系及未验证项；
- 对性能/测试时间/代码重复率的改善只报告**实际测量数据**，不编造；
- 超过默认规模的拆分计划或获批的例外；
- 仅经明确许可把 `test` 晋级 `main`，不得强推、绕过分支保护、私自发 Release。

本规范针对工程复杂度，不限制合理的安全修复，也不授权关闭或削弱任何现有强制测试。
