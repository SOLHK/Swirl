## Observed defects and uncertainty

The old product option defaulted to OFF, its production staging was conditional,
the DLL error discarded Qt's reason, and EXE/DLL matching only checked ABI=1.
Cargo input dependencies omitted vendored source and toolchain changes. Existing
packaging paths also assumed `rust-target/release` and did not run a paired
EXE/DLL validation before acceptance.

Those are verified source/build defects. The user's Windows installation and
419 private nodes are unavailable in this Linux workspace. A screenshot of the
generic message cannot prove whether that installation is missing the DLL, a
dependency, the correct architecture, or a matching build. Do not claim its
specific native loader root cause has been observed.

## Implemented fixes

- Product Rust is mandatory; explicit OFF fails. Independent font tests retain
  their separate configure path.
- Cargo runs incrementally on every product build, with an explicit architecture
  target. Failure cannot fall through to copying an old DLL.
- Rust source/manifests/vendor/toolchain plus revision form a content identity
  shared by Qt and Rust. Changes force reconfiguration and paired rebuild.
- The runtime library is copied even if Qt does not relink. Staging uses actual
  target output directories and records `swirl-rust-build.json`.
- `RustCoreLibrary` uses an absolute adjacent library, validates bounded PE
  headers on Windows, and checks all required exports, ABI, build ID and SHA.
- Actual `QLibrary::errorString()` is retained. A separately labelled native
  `LoadLibraryExW` diagnostic captures GetLastError immediately; the code never
  mislabels a stale post-Qt error as Qt's original error.
- Win32 126 alone does not identify a specific missing dependency. Loader
  success establishes load-time imports; delay-loaded later dependencies are
  not claimed to have been exercised.
- Bounded metadata is field-validated and whitelisted; node config, passwords,
  tokens and subscriptions are never part of the diagnostic.
- `Swirl.exe --rust-core-self-test REPORT.json` loads the actual DLL, starts a
  Rust listener, performs real HTTP/CONNECT/SOCKS5 loopback requests, checks
  response bytes and counters, then verifies listener cleanup. It does not
  access NodeStore or change system proxy/DNS/TUN. Separate UI smoke is required.
- New Windows MSVC workflow stages into a fresh product directory, runs the EXE,
  tests missing-DLL rejection, starts QML, and packages only after success.
