# D1 → A3：Windows 目标端输入精度交接

本文件只交接 D1 独立分支 `work/vf-windows-d1` 的目标端证据。
源端 Apple 机制由 A3/窗口 2 继续研究；D1 没有修改 Apple 算法。

最终可执行源码：`41504fed7ec7ca6d4768389106a03aa9bc5cd36e`。
最终 Windows run：[39401509155](https://github.com/SOLHK/Swirl/actions/runs/39401509155)，
两套 Server Runner 均完成，严格 CI 最终为 **failure**；每套 12 个完整进程、
3568 条观测通过独立验证，4 个 FreeType 路径一致性失败保留。
原始分析报告与固定对象诊断数据已保存在本文末尾链接的仓库 JSON 中。

## 当前可采用的结论

`499.006199` 与 `499.006201` 经 Qt `float` / DirectWrite `FLOAT` 输入时，
均为 `499.006195068359375`，二进制位 `0x43f980cb`。
该处相邻 binary32 间距是 `0.000030517578125`。
两者的最近 16.16 编码也相同（`32702870`），但本次反证不依赖假设
Windows 必须先执行用户坐标 16.16 舍入：在公开轴 API 入口处区别已经消失。

在未改变轴参数语义、没有额外旁路信息的确定性渲染路径中，相同的完整输入
无法选择两个不同的目标输出。尚未验证任何能通过当前 Qt/DirectWrite
公开轴接口保留这对原始十进制请求差别的方法。

### 实际 Windows 证据

第一阶段源码：[`562cbc998d03ad36c7e8b25fa7c614a3b17168ae`](https://github.com/SOLHK/Swirl/commit/562cbc998d03ad36c7e8b25fa7c614a3b17168ae)。
真实 Windows run：[`39399001699`](https://github.com/SOLHK/Swirl/actions/runs/39399001699)。
Windows Server 2022 Datacenter，build `20348`；dwrite.dll `10.0.20348.1`。

两份原创夹具 × 直接文件/系统安装加载 × 独立正/反序进程，共 8 个 DirectWrite
进程、448 条完整观测。上述输入对在以下观测中一致：完整轮廓操作与坐标位、
设计度量、自然排版 advance、实际 alpha 像素。结论不是从 API 回读相同推导的。

| 夹具 | 两个请求各自的 A advance | 两个请求各自的 A 轮廓最右坐标 |
| --- | ---: | ---: |
| ordinary | 636 | 536 |
| gain | 19000 | 18060 |

多轴端点控制确实改变轮廓与像素；wght/WDTH 还改变水平 advance。
对 gain 的 28 个固定输入，预声明的 normalized16-before-avar 模型在 A advance
和最右轮廓坐标上残差均为 0；连续与 user16-continuous 模型最大残差约 204，
normalized14-before-avar 模型残差 6000。普通夹具仍有 0.3603515625 FUnit
的未舍入模型残差。有限样本吻合不能证明全部 Windows 内部计算步骤。

独立记录的 API 回读还显示：`100.00000762939453125` 回读为
`100.0000152587890625`，与后者输入的回读相同。这支持该控制点发生用户坐标
16.16 规范化的解释；normalized16 模型吻合并不排除“先 user16、再 normalized16”
的组合路径。回读和实际轮廓必须继续分别分析。

另一个控制恰好说明“回读不同”也不等于“字形不同”：
`499.00616455078125` 与 `499.0062255859375` 的输入和回读分别保留
`0x43f980ca`、`0x43f980cc`，但 gain 夹具仍均得到 A advance `19000`、
最右坐标 `18060`，完整轮廓与栅格相同。

### 与源端反例合并后的条件下界

集成分支交接文件记载 CoreText GID 5 的 advance 差为
`0.5474853515625 FUnit`。若 A3 继续要求这两个请求使用相同的公开目标轴值、
由同一个确定性目标输出拟合，那么至少一端的误差不小于
`0.27374267578125 FUnit = 8.759765625 × (1/32 FUnit)`。

这是对当前输入契约的阻塞，不是对所有编码方案的否定。任何重新参数化、
增加轴/离散选择、预生成静态实例或自定义渲染器的替代方案，都需要单独定义
输入契约并重新证明源端和目标端的等价性；本轮没有把这些未经测试的方案写成通过。

## Qt 状态与必须保留的失败

第一阶段 Qt 6.10.3 native 路径完成实际路径、advance、布局和像素检查；
每个进程覆盖 9/12/18 pt、96/144 logical DPI、1/1.25/1.5/2 DPR。
但 Qt 接收并消费了 `--reverse`，因此独立反序进程的标签不成立；进程内部的反序
与私有字体移除/重载检查已经运行。第二阶段改用 `--reverse-order` 并独立核对 header。

四个 FreeType 进程均在首个场景发现路径坐标相差 1/64 px，原始 advance、
字形 ID、布局位置及绘制像素相同。该问题没有被当成小数输入精度保留，也没有
通过放宽阈值、预热或删除失败变为 PASS。隔离诊断子进程将观察同一请求在绘制前后
的路径状态。第一阶段整个 Actions run 的最终状态是 **failure**。

首轮 Windows 2025 job 没有完成原生编译，原因是 VS2022 generator 与已安装
VS2026 不匹配；第二阶段改为发现并记录实际工具链。原生新结果以对应源码 SHA
的后续 run 和 `d1-analysis.json` 为准，不继承首轮的预期。

### 第二阶段更新：两个 Windows 环境均已实测

源码 [`47d6dfc06fa2fddddd1532c1d8370028a6b9da17`](https://github.com/SOLHK/Swirl/commit/47d6dfc06fa2fddddd1532c1d8370028a6b9da17)，
run [`39400461390`](https://github.com/SOLHK/Swirl/actions/runs/39400461390)。
Server 2022 / 2025 均完成编译与原生运行；每个系统 8 个 DirectWrite 进程
通过，共 448 条观测；4 个 Qt native 进程通过，共 3120 条观测；
4 个 Qt FreeType 进程仍严格失败。两个系统之间对应的 DirectWrite 和 Qt native
完整 payload 均一致。独立反序参数已生效，安装与清理均通过。

FreeType 原因已缩小为**绘制历史影响路径读取**：保持同一个 `QRawFont` 和
完全相同的 `499.006199` 输入不变，A 最右坐标在绘制前为 `6.421875 px`，
绘制后立即变为 `6.4375 px`。重复相同十进制以及改为另一小数请求都保持后者；
反序请求还会交换哪个小数首先得到前者。8 个隔离诊断子进程结果完全相同。
A advance 始终 `7.625 px`，三次绘制的像素 hash 完全相同。
因此不能把首轮不等的 QRawFont 路径解释为保留了原请求精度。

Qt 6.10.3 的 raster 路径设置 FreeType 子像素平移，path 路径仅在矩阵不同
时重置变换，这与观测一致。第三阶段继续用固定单字形与不同绘制偏移验证该机制，
不放宽主检查、不清除失败。Swirl 基线 `FontRendering.h` 默认请求 FreeType，
所以此项必须进入后续适配交接；当前数据也不足以宣称 Swirl UI 已出现可见回归。
第二阶段 run 的最终状态仍为 **failure**。

### 第三阶段最终结果：固定对象的子像素状态实验

最终源码 `41504fed7ec7ca6d4768389106a03aa9bc5cd36e` 已在两个真实 Windows
Runner 完成。37/37 Python 测试均通过；DirectWrite、Qt native、安装清理、
正反顺序和私有／安装比较均重复第二阶段结果。完整严格验收仍未通过，
分析器不会把部分证据转写为 PASS。

在同一个 `const QRawFont`、同一个 A 字形、固定 `499.006199` 轴输入下：

| 前一次绘制 x 偏移 | 后续查询的 A 左端 | 后续查询的 A 右端 |
| ---: | ---: | ---: |
| 0 | 0.71875 | 6.421875 |
| 0.25 | 0.71875 | 6.4375 |
| 0.5 | 0.71875 | 6.4375 |
| 0.75 | 0.734375 | 6.4375 |
| 重放 0、0.75、0.5、0.25、0 | 0.734375 | 6.4375 |

8 个诊断子进程均得到相同的三种路径，advance 始终 7.625 px；同一偏移的
位图重放精确一致。72 张 PNG 已重新解码核对像素哈希与墨色像素数，全部相符。
这直接证明固定字体对象的路径查询受先前栅格化位置与历史影响；缓存命中提前返回、
残留 FreeType 平移的具体解释由固定版本 Qt 源码支持，未使用私有 API 读取内部状态。

此项测试使用 `PreferNoHinting` 的 QImage；Swirl 生产配置请求
`PreferFullHinting`。实际 Qt Quick UI、清晰度、性能仍未验收。不能从路径查询
问题推断已经出现可见 UI 回归，也不能据此宣称原版目标精度已经保留。

## 自动适配基础与最终验收入口

独立 Qt 可执行程序读取夹具真实家族/轴元数据、验证实际字体表身份，并直接编译
已有 `FontAxisPolicy.cpp`，不修改共享生产文件。新增 36 项策略检查覆盖自动字重
400/600、96/144/192 DPI、1/1.25/1.5/2 DPR、自定义轴默认值，以及手动
`wght=623.25, WDTH=137.5, HGHT=172.5` 和错误大小写 `wdth` 的拒绝。
自动默认字重和 600 字重还进入 Qt 实际渲染矩阵。

目前没有合格原版候选 TTC。以下内容全部保持 **NOT_RUN**，不可由合成夹具代替：
