## 候选究竟改变什么

`T(x)=trunc(x×10000)/10000` 是本实验使用的可证伪外部模型，不是对 Apple 私有函数的命名。这里 x、乘法结果和除法结果均按 binary64 求值，`trunc` 向零取整；不能改成精确 Decimal，也不能把除以 10000 重排成乘以 0.0001。例如 x=415.09865 得到 T1=415.0986，而 T1 的 binary64 乘积为 4150985.9999999995，因此 T2=415.0985。旧 readback 计划仍为 `C=T(T(x))`，由原始输入预先计算。三个候选的设计输入为：

| 模型 | 严格 identity avar 轴 | 非 identity avar 轴 |
|---|---|---|
| 旧 ENDPOINT 控制 | C | C |
| ONCE_ALL | T(x) | T(x) |
| ONCE_IDENTITY | T(x) | C |

设计输入之后的算法不变：严格 identity 负半轴使用 `float32((value-min)/(default-min))-1`，identity 正半轴使用 binary64 归一化；非 identity 轴使用 `float32(normalize(value))`。随后 normalized16 向零截断、按原始表序执行 avar、nearest F2DOT14。identity 分类依据完整原始记录结构，重复记录不会被排序、覆盖或去重。

所有模型及设计阶段输入在原生进程启动之前写入报告。原生 original 请求始终是未经替换的完整 binary64 三轴 `x`；replay 始终是旧 C。模型函数不读取原生观测，不按 face/GID/实测误差切换公式。

结果支持“设计映射不应直接采用最后读回值”的阶段分离。它不能唯一确定 CoreText 内部的运算指令或排除其他在有限输入上等价的公式。

## 输入精度障碍仍是有条件的不可能性

原 face 15 完整输入 `(500,499.006199,500)` 与 `(500,499.006201,500)` 仍有相同标准用户 16.16 整数 `32702870`、相同 binary32 bits `43f980cb`，而实际 Apple 设计状态为 q=0/65。旧 35 GID 原始证据中的 31 个 payload 差异、GID 5 advance 差 `0.5474853515625 FUnit` 全部保留。

若目标只保留这个已经合并的输入状态，且没有其他侧信道，同一确定性输出对两端的最坏误差至少为差值的一半，即 `0.27374267578125 FUnit`，是 `1/32` 的 8.759765625 倍。更换 avar 表、平滑跳变或提高容差都不能恢复已丢失的输入信息。

[OpenType 归一化规范](https://learn.microsoft.com/en-us/typography/opentype/spec/otvaroverview#coordinate-scales-and-normalization)要求输入先转成 16.16，再以 16.16 进行归一化及 avar 运算，最后得到 2.14。这里的规范入口约束应与 q 的表示能力分开：0 和 65 都能准确写成 F2DOT14。保留原始 binary64、独立求出不同 q 后使用 normalized 接口，不满足“目标输入先合并”的前提。

原始 avar 的重复 fromCoordinate 不符合[标准 avar 的唯一、递增要求](https://learn.microsoft.com/en-us/typography/opentype/spec/avar)；Apple 对该原件的顺序行为必须靠原生证据约束。不能把 Python 字典覆盖后的表当作原始表，也不能由标准表语义直接推导这个非标准原件的行为。

## 提议给生产负责人的最小集成方向

本轮可以提议审查 **ONCE_ALL 实验候选**，不直接改生产。其证据比“误差在门槛内”更强：独立 holdout 上实际 HVAR 和已预选的直接 HVF 为零；其范围仍只覆盖本轮位置及 GID。

集成设计应明确保留三个字段：原始 binary64 请求、用于计算 q 的独立设计阶段值、实际原生读回。缓存或序列化不能把最后一项当作第一项的替身；测试已证明相同读回可以有不同 payload。预声明 C 仍只服务于原有 replay 诊断，不能悄悄变成设计映射输入。

若目标能够在丢失 binary64 前计算并提交正确的完整 normalized 向量，存在可实现的兼容通道；若目标只暴露会合并这两个请求的用户 FLOAT/16.16 入口，原精度目标对该输入对不可能同时成立。这个分支结论不改变轴范围，不取消原反例，也不宣称任意目标 API 已兼容。

独立并行提交 `73a5bc831c46b25c3480c9d28eae4216b5add2b3` 的 [CI 39406852651](https://github.com/SOLHK/Swirl/actions/runs/39406852651) 提供 Linux 和 Windows Server 2022/2025 上真实 HarfBuzz/FreeType normalized glyph 控制，三平台各 72 观测、36 反序对、64 normalized glyph 检查全相等。其字体为原创合成 fixture、q 由外部提供；HB 验证 advance/extents，FT 验证 advance/完整四点轮廓。它没有求解 Apple 用户到设计映射，也没有验证 DirectWrite、Qt 或 Swirl。这里只读取共享证据，没有代替窗口 5 开发或重新运行 Windows 目标测量。
